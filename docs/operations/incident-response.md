# 应急响应

## 原则与分级

数据正确性和密钥安全优先于缓存实时性与局部可用性。PostgreSQL 是唯一权威事实源；不得用 Redis、日志、客户端状态或 Worker 观察反向覆盖正式事实。

- SEV-1：权威数据库不可用或疑似损坏、Flag/Session/密钥泄露、成绩事实被未授权修改、全站不可用；
- SEV-2：实例 Provider、对象存储、邮件或多个控制面副本持续故障，比赛核心能力部分受影响；
- SEV-3：单副本、缓存、实时事件或个别任务故障，有明确降级路径且不影响事实正确性。

## 响应流程

1. 建立事件编号、负责人、时间线和独立沟通频道，记录所有操作人和命令。
2. 止损：隔离受影响副本/凭据/Provider，暂停危险写操作或新实例领取；不要删除证据。
3. 保全：保存不可变审计、结构化日志、OTEL trace、数据库和对象存储恢复点、相关任务/实例标识。导出前先脱敏。
4. 判断权威事实的最后可信时间，明确受影响比赛、队伍、题目和时间窗口。
5. 按组件 Runbook 恢复；恢复后重放成绩、重建缓存、执行实例对账和附件摘要校验。
6. 对外沟通只说明确认事实、影响和下一次更新时间，不泄露 Flag、答案、Cookie、邮箱令牌、密钥、内部地址或漏洞利用细节。
7. 关闭事件前完成业务 smoke、健康检查、队列清零/解释、审计核对和负责人确认。
8. 事后复盘根因、检测缺口、恢复耗时、数据影响和防复发任务。

## 组件处置

### PostgreSQL

立即阻止新业务写入并保留现有副本。确认是连接、容量、锁、复制还是数据损坏问题。只有在当前主库无法安全恢复时，才按备份恢复文档在隔离环境验证 dump、对象版本、摘要和排行榜重放，再切换。不得从 Redis 或应用日志拼回成绩事实。

### Redis

保持认证、提交和实例所有权逻辑使用 PostgreSQL。限制排行榜昂贵重建，允许读取持久快照并标记短期陈旧；恢复后执行 `cache_rebuild`，核对版本，再恢复实时扇出。

### Worker 或 Kubernetes API

停止或降低实例任务领取，保留任务租约、期望代次和错误分类。控制面继续提供非实例业务。API 恢复后运行 `instance_reconcile`，仅管理具有完整平台所有权标签的资源；未知资源只报告，不直接删除。

### 对象存储

停止新上传提交和受影响下载，保留数据库内容引用。不要把本地临时文件当作权威副本。恢复版本化对象后核对数据库记录的 SHA-256，再开放流量。

### 邮件

安全事务和站内通知不回滚。保留 `mail_deliveries` 重试状态，修复 SMTP 后幂等恢复投递；避免手工重复发送一次性令牌。

### 控制面副本

摘除不 ready 副本并保留日志。其他副本可从 PostgreSQL 和 Redis 继续服务。若错误与发布相关，回到与当前 schema 兼容的构建；禁止恢复旧公网 Go 写路径。

## 凭据或敏感数据泄露

立即撤销相关 Secret、限制访问并保全证据。按影响轮换 Session 密钥、提交答案密钥、实例密钥、数据库/Redis/S3/SMTP 凭据；对用户执行 `session_invalidate`。轮换实例 keyring 时保留仍需解密活动实例的旧 key，先停止新信封使用旧 key，再销毁或迁移引用，最后移除。疑似 Flag 泄露时冻结相关题目或比赛处置窗口，保留提交事实，由有权人员决定修题和计分调整并写审计。
